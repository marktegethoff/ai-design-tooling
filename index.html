Team Lead

Getting Your Team on the System

Sequence matters. Follow this order. Do not start with infrastructure.

Deployment sequence

Teams that start with infrastructure setup without the proof and vocabulary foundation treat the CLAUDE.md as a config file, skip the commit ceremony after two weeks, and conclude "it didn't really change how we work." The sequence below is causal, not sequential.

1

Share the capability proof first

Run the case study at a team session before any tooling setup. People must see what the system produces before they'll engage with how it's structured.

2

Run the vocabulary workshop

One session, 45 minutes. Introduce: behavioral contract, design intelligence infrastructure, brief (not prompt), direct/assisted/authored. End with a live demo of a CLAUDE.md edit changing Claude's behavior.

3

Draft the org layer CLAUDE.md

3–5 rules. IP handling. Accessibility floor. Brand voice non-negotiables. Get legal review. Keep it thin so it clears quickly. See the org template.

4

Build a team CLAUDE.md template

One template per platform team. Import the org layer. Include the decision hierarchy. Give teams the template at their first session, not before — they need the vocabulary to use it well.

5

Work with IT on the onboarding package

Define what needs to be pre-deployed: Claude Code installation, team CLAUDE.md, agent directory, skills directory. Provide a package spec; IT handles deployment via MDM. Target: zero terminal interaction for setup.

6

Launch the commit ceremony

Start with a #design-decisions Slack channel. Give teams the entry template. Run it for 4 weeks before evaluating whether a git-backed memory sync is worth adding.

warning

Do not skip steps 1 and 2

The sequence is causal, not sequential. Proof and vocabulary create the conditions where the infrastructure lands. Without them, it's just tooling — and tooling without context gets abandoned.

Governance: the three-layer model

The three-layer stack uses Claude Code's native @filename imports — org layer, team layer, personal layer. Each extends the one above. No custom tooling required.

info

Full model documented in Behavioral Contract

The complete three-layer governance model — what belongs in each layer, how they compose, and the layer ownership rules — is in Behavioral Contract. The templates are in Reference.

warning

Keep the org layer thin

If the org layer becomes opinionated about craft — component patterns, visual style, prompt strategy — people will reject it as top-down prescription. The org layer's authority comes from its restraint. It governs only what the org must govern.

The commit ceremony

Every team has tried a shared knowledge system. Most die within six weeks. The cause is always the same: contribution is voluntary, asynchronous, and competes with real work. The commit ceremony solves this by making contribution synchronous — it's the closing ritual of every session, not a separate task.

Voluntary contribution

"Remember to update the docs after the session." Nobody does. The record is always 3 weeks behind.

compare_arrows

The commit ceremony

The session isn't closed until someone writes the sentence. One rotation. One sentence. The record grows every session without any separate effort.

What makes a good entry

TypeGood entryWeak entry
Decision "We use a single bottom sheet for all filter states — multiple sheets created context-switching overhead." "We decided on the filter design."
Discarded direction "Rejected tab-based navigation — tabs imply parallel content, our flows are sequential." "We tried tabs and didn't like them."
Named constraint "The transaction list must render within 200ms — anything slower breaks the sense of responsiveness." "Performance matters for the transaction list."
tips_and_updates

Use a #design-decisions Slack channel with a one-sentence template as the commit surface. Git write access at an enterprise can take 2–4 weeks to provision. Sync to the shared repo weekly in the background. Nobody needs to touch git to participate.

Case Study

What the right infrastructure makes possible.

Your AI Tooling lead used this methodology to build a production-quality iOS app — where your words are the artifact and the AI is the archivist — with the scope that previously required a full team.

tips_and_updates

The product is private IP and is not named here. What is documented is the methodology — the system structure, the decisions made, the practice that evolved, and the honest account of where judgment was irreplaceable.

What I actually learned

A personal account of how this practice was built — what worked, what broke, and what I still don't know.

How I started

I didn't start with Claude Code. I started in ChatGPT, building an app I had no idea how to build.

I'm a designer. I have opinions about product strategy. I understand systems. I'd never written a line of Swift. But I had an idea about friction. Every time you open a notes app, there's a silent question: where does this go? What is it? The pressure to title a note — to name the thing before you've said it — is one version of that question, and it's the one I kept thinking about. It sounds like a small thing. It's almost embarrassing to describe. But the research on task-switching is pretty clear that even a trivial switch carries an irreducible cost — and when the task you're switching away from is the thought itself, still forming, the switch isn't just overhead. It degrades what you were encoding. The moment you answer the structural question, some of the thought doesn't come back. Not everyone feels it. I do, and I suspect I'm not alone. I wanted to build something that removed that question entirely: capture first, structure later, imposed by a system working behind the record. I approached it the way I approach design: start with the ethos, define the principles, build the system before you build anything in it. I spent weeks in ChatGPT working out what the app should stand for before I wrote a line of anything.

Then I needed to actually build it. I opened Claude, and my first serious session involved asking it — step by step — what to click in Xcode to create an iOS project. Not "how does SwiftUI work." Literally: what do I click. That was the starting point.

What I learned in that first phase was how much I didn't know I didn't know. I thought setting up agents meant I had structured AI collaboration. I didn't — the agents weren't installed anywhere that persisted between sessions. I thought HTML prototypes would tell me something useful about iOS. They didn't — the medium actively misleads you about what the native platform will actually feel like. I was making confident decisions on a shaky foundation.

What broke

The first thing that broke was the prototype-to-production translation. I'd validated something in HTML that couldn't work the same way on iOS. The feedback from the prototype was real feedback about the wrong thing. I had to build a dedicated prototyping environment — a lightweight SwiftUI canvas, separated from the production codebase — to get feedback that was actually legible for what I was building.

The second thing that broke was context. I was having what felt like conversations with a team. The interface was fluid. The responses were coherent. And then an agent would produce a beautifully reasoned recommendation that was confidently wrong — not because the reasoning was bad, but because the agent didn't know what I knew. It had the context I'd given it in that session. It did not have the context I'd accumulated over months of work.

This is the thing I most want you to sit with, because it's the insight I see people miss most often: when you're having a natural language conversation with what feels like a collaborator, you forget the system is stateless. There is no persistent memory unless you build it. An agent can produce a well-reasoned rationale and be completely wrong about the system it's operating inside — and the rationale will feel convincing precisely because it's well-reasoned. Evaluating that output requires knowing more than the agent does. That knowledge doesn't exist anywhere except what you've built and maintained.

I built a lot of infrastructure around this problem. Sixty-four architectural decisions, logged and indexed — so nothing gets re-litigated in session 12 that was resolved in session 4. Memory files that load at session start and give agents the current state of the system. Specifications that codify exactly what a surface should do before any code is written, so the engineer agent and the design agent are working from the same document. A session start protocol that confirms scope before a token is spent. The context has to be actively built and maintained. It doesn't accumulate automatically.

What I built

What I actually built is a mech suit.

Not a replacement. Not automation. Something that extends what I can do — that fills in capabilities I don't have while leaving the judgment where it belongs.

I don't know Swift. But my system speaks a technical language fluently, and working inside it means I've learned to speak it too. I'm not more technical than I was. But I ask better questions, I challenge weak answers, I understand tradeoffs in the data model in ways I didn't before. The system teaches me as I use it. That was not something I planned for — it happened as a consequence of the way the work is structured.

I also built a team that argues. That part I did deliberately, even if I wasn't sure it would work.

The specific failure I was trying to prevent: one person with complete context, building a product where the user is themselves, running decisions through agents that are wired to agree. A closed loop. The longer it runs, the more it confirms itself. I've seen this in teams — the longer a team goes without real friction, the more their decisions start to look inevitable to themselves and arbitrary to everyone else.

So I engineered friction. There's a culture document in the system — not a configuration file, an actual statement of how the team works. "Argue hard. Commit fully. Trust the craft." And the individual agent files go further: the Critic's file describes the Architect as the discipline most likely to resist its cuts, and gives explicit instructions for how to handle that resistance. The Marketer's file describes its working relationship with the Architect — one explodes scope, the other prices it. The Strategist is required to engage with the Historian's evidence even when it argues against the Strategist's position. These aren't personality quirks. They're designed accountability relationships.

I'll be honest about what I can and can't claim here. The hypothesis is that designed opposition between agents — where the tension is baked into the agent definition, not imposed procedurally from outside — produces more genuinely diverse reasoning than either a single agent or a team of agents with different system prompts but no encoded relationship to each other. The historical precedent supports it: red teams, devil's advocate roles, legal adversarial process all show that mandatory counterposition prevents the confirmation drift that kills creative judgment over time. But I can't prove the AI version works better. I can only say it lines up with the theory, and that without it, I'd have no friction at all.

I also built synthetic users for the same reason — archetypes that represent the different ways people actually use the kind of product I was making. The Thinker, the Reviewer, the Processor. The user I've been building for is me. That's useful and also dangerous. Synthetic users are the counterforce.

What I didn't expect to relearn

I spent fifteen minutes recently trying to describe a layout problem to Claude. What I was trying to communicate was spatial — a relationship between elements on a surface, a proportion question, a question about hierarchy under different content conditions. I kept restating it. The responses were coherent and kept missing the thing. Then I stopped, sketched it on paper, took a screenshot, and dropped it in. The conversation resolved in two exchanges.

The sketch wasn't a deliverable. It was the kind of thing I'd have drawn on a whiteboard to get aligned with a colleague — rough, structurally accurate, enough to give the idea shape without giving it form. That's what made it work. Not the image itself, but what the image communicated: the idea, directly, without the translation loss that comes from converting a spatial relationship into a verbal description of a spatial relationship.

The text interface creates a pressure that's easy to absorb without noticing. The tool speaks in text, so maybe the work has to happen in text. It doesn't. The gravitational pull is real — when your primary interface is a prompt box, your visual tools start to feel like things you're meant to work around rather than with. That's worth resisting. Visual input is a full channel. For anything spatial, anything about proportion or relationship or structure, it's often the sharper one. Figma exports, design screenshots, rough sketches: the AI sees what you show it. Show it the thing.

The secondary observation: the rough sketch isn't just faster to communicate than a verbal description. It might also be a reason to pick up a pen before opening a tool. The constraint of analog forces a different kind of thinking — more structural, less component-driven. Whether AI collaboration quietly brings that back as a side effect is something I'm watching. It would be an odd but welcome outcome.

What I still don't know

The honest version: I don't know how this translates to a team.

What I've built works because I'm one person with complete context — I'm the designer, the product manager, the QA, and the end user. The infrastructure I've described exists to extend that one-person context across time, not across people. A team is a different problem. Multiple people building shared context, with different backgrounds, different mental models, different relationships to ambiguity. Their questions won't be my questions.

I have a point of view on what matters — behavioral contracts that persist, memory that accumulates, quality gates that enforce the process. But the honest answer about team translation is that I haven't had to solve it yet. What I can tell you is what it's been like for one person, and what I believe is transferable. Where the evidence stops, I'll tell you it stops.

That's what this site is: the transferable part, documented carefully, with the honest account of where judgment is still required.

One decision, shown in full

A single prompt asking Claude to "design the navigation model for a content-dense mobile app" produces one answer — usually the obvious answer. The methodology produces a reasoning trail.

The problem: A mobile app requires simultaneous access to three persistent states — a content record, a compose surface, and an organizational view. Standard navigation patterns (tab bar, navigation stack, modal sheets) each fail a specific requirement: tabs imply parallel content of equal weight; stacks imply hierarchy that must be traversed; modals imply temporary interruption. None of these match the actual model.

Problem
Three persistent states. No standard navigation pattern fits. Any choice forces a compromise.
arrow_downward
Historian
Tab bars: fail. Imply equal-weight parallel destinations — one state here is dominant. Nav stacks: partial. Depth navigation is correct for one transition, not all three. Spatial models (Palm OS, early iOS): survived when states exist simultaneously in physical space, not hierarchically.
arrow_downward
Architect
Constraint: the three states must coexist spatially, not sequentially. A gesture model is required — the user moves between states, not navigates to them. Two detent positions define the rest state and the exposed state of each surface.
arrow_downward
Critic
Remove the tab bar — permanent chrome for a model where one state is always dominant is visual noise. Remove the modal for organizational view — dismissal creates context loss that breaks the spatial metaphor. Keep the nav stack for depth transitions only.
arrow_downward
Designer
Gesture-driven horizontal spine. Two detent positions: rest (content dominant) and revealed (organizational view exposed). Compose surface always accessible via gesture, never requiring navigation. Haptic feedback at detent crossings. Spring animation to snap target.
arrow_downward
Creative Director
INEVITABLE. The spatial model is the only solution that satisfies all three requirements simultaneously. Nothing can be removed without losing a constraint. Nothing was added that the constraints didn't require.
lightbulb

A single prompt produces one node. This process produces six — each one eliminating options that seemed viable until examined. The reasoning trail is the output. The navigation model is a consequence of the trail, not the other way around.

The result: no tab bar. Cabinet, Timeline, and Compose coexist at fixed spatial offsets — the interface shifts to reveal, it does not navigate. Three persistent states, zero tabs, gesture-driven.

The honest account

Most case studies show what worked. This one is incomplete without showing where the methodology was tested — where the system produced output that was structurally wrong, where judgment was the only tool available, where the process nearly failed.

01

Knowing when to skip the workflow

The full methodology is expensive. A bug fix that runs through Historian → Architect → Critic → Designer → QA is absurd. But a bug fix that reveals a structural failure — where the root cause is a design decision made three months ago — is not a bug fix. It requires the full pass.

The methodology cannot tell you which one you're looking at. That judgment is irreplaceable.

02

When the agent is convincing and wrong

A Critic agent will remove things. That is its job. On one pass, it removed a component that appeared redundant — its rationale was structurally coherent, well-reasoned, and wrong. The component was doing work that wasn't visible in the context the Critic was given.

Agents produce output shaped by the context they receive. A well-reasoned rationale is evidence that the agent understood its prompt — it is not evidence that the agent understood the system. Evaluating agent output requires knowing more than the agent does.

03

When two principles pointed in opposite directions

The decision hierarchy resolves most conflicts. But there were decisions where structural correctness and system coherence were genuinely in tension — where the most structurally correct solution for this component broke the coherence of the broader system it lived inside.

The hierarchy doesn't resolve this. It names the conflict more precisely. The resolution required understanding what the product was becoming — not just what it was. No agent holds that understanding. It accumulates through the work.

How the practice evolved

This methodology was not designed in advance. It was grown in response to what the previous version couldn't do. Each inflection point exists because the prior state failed in a specific, legible way.

01

Building directly in production

Failure mode: design decisions validated in the wrong environment. Prototyping and implementation are different cognitive modes.

Response: a dedicated design canvas — separated from the production codebase, built for prototyping without production constraints.

02

Single discipline commands

Failure mode: one agent, one answer. No reasoning trail. Inconsistent output quality.

Response: sequential workflows — multi-agent processes that enforced a reasoning sequence. You approve each stage before the next begins.

03

Workflows without enforcement

Failure mode: the sequence existed but wasn't enforced. Gates were voluntary. Good process that isn't enforced is just documentation.

Response: hard skill gates — the design workflow cannot write to production without a canvas prototype. Engineering cannot begin without a specification.

04

Generalist agents for all work

Failure mode: a generalist AI produces mediocre output at every specialty. Each discipline requires a different lens.

Response: 23 specialist agents, each scoped to a single lens, each assigned the right model for its task.

05

Specialist agents, no quality arbiter

Failure mode: good specialist output across disciplines produced inconsistent final quality. No agent evaluated the whole.

Response: Distinguished Engineer and Creative Director as terminal quality gates. SHIP / REVISE / REJECT verdict before anything moves forward.

lightbulb

The most valuable practice isn't on this list

Each inflection point above is something added. The practice that compounded more than any of them was subtraction — learning to solve the problem before reaching for the tool, to run the critic pass before the design pass, to ask whether the prototype was necessary before opening the canvas.

The AI makes it effortless to act. Restraint is what makes the action worth taking. This cannot be installed. It has to be practiced. But it can be named — and naming it is the first step toward building it as a team habit.

The methodology doesn't replace a team — it closes the access gap. The scope that previously required coordinating ten people becomes accessible to each person working within it. The setup guide walks through exactly how to get started — in the right sequence, with the right foundations in place.

The Behavioral Contract

A CLAUDE.md is not a config file. It is a contract that governs how your AI collaborator behaves — encoding your philosophy, decision hierarchy, and constraints into every session.

What changes when you name it correctly

Called a "config file"

Treated as IT setup. Written once, never updated, stale within a month. Claude's behavior drifts from team standards. No one feels responsible for maintaining it.

compare_arrows

Called a "behavioral contract"

Every edit becomes a decision with consequence. People debate what goes in. Updating it feels like craft, not housekeeping. The contract evolves with the team's standards.

lightbulb

The live demo is required

The phrase only lands if someone edits the CLAUDE.md and immediately sees AI behavior change in response. Without that visceral before/after, "behavioral contract" is just a slogan. Start every introduction with a live edit and its consequence.

What belongs in a behavioral contract

gavel

Non-negotiables

Brand rules, IP handling, accessibility floor, tone. These are the org layer — they must never be overridden downstream.

design_services

Team standards

Design system tokens, component vocabulary, platform conventions, decision hierarchy. How this team makes decisions.

psychology

Process philosophy

What the AI should never do. What it should always do. How it should surface uncertainty. Anti-patterns that are treated as defects.

warning

Agents and skills are not guardrails

Claude Code agents and workflow skills encode process, not enforcement. They guide the sequence of work and surface the right questions — they do not prevent bad output or enforce compliance. Judgment remains with you.

The decision hierarchy

When Claude makes a judgment call, what order should it apply criteria? Encoding this explicitly prevents arbitrary output.

1

Structural correctness

Does the solution solve the actual problem?

2

Conceptual clarity

Is the concept legible without explanation?

3

System coherence

Does it fit the design system and platform conventions?

4

Reduction of parts

Can anything be removed without losing function?

5

Craft precision

Is the execution correct at the detail level?

6

Visual refinement

Does it look right?

tips_and_updates

Add this hierarchy to your team CLAUDE.md verbatim. When Claude produces output that prioritizes visual polish over structural correctness, the hierarchy is missing or not being enforced.

The three-layer governance model

Claude Code supports @filename imports inside CLAUDE.md natively. The three-layer stack uses this — no custom tooling required.

1

Org layer — org-behavioral-contract.md

Non-negotiables. IP handling. Accessibility floor. Brand voice. 3–5 rules maximum. Protected — doesn't change without review.

2

Team layer — CLAUDE.md

Platform-specific context. Design system vocabulary. Team decision hierarchy. Owned by the team lead, updated at retrospectives.

3

Personal layer — @me.md

In-progress work, personal context, temporary state. Never overwrites the org or team layers. Cleared or updated each session.

Agents & Skills

Specialist agents apply a single lens. Skills orchestrate them into sequences with gates and pauses. Together they encode process, not just prompts.

warning

Agents are not bulletproof

An agent's defined scope is a behavioral instruction, not enforcement. Claude will follow the scope while the conversation is fresh — but in long sessions, or with contradictory prompts, it can drift. Check agent output the same way you check any AI output: read it, verify it, apply judgment.

Two categories

Discipline agents

Single-purpose specialists. Each applies one lens: Historian surfaces precedent. Critic removes unnecessary elements. Architect defines data models. Designer specifies interaction states. They bring specific analysis, not final decisions.

add

Workflow skills

Slash commands that route work through a sequence of discipline agents. A design workflow might invoke Historian → Strategist → Architect → Critic → Designer in order. The orchestrator manages the sequence; you approve each gate.

Model assignment by role

Assigning the right model to each agent reduces cost and latency without sacrificing quality.

ModelBest forExamples
HaikuClassification, gates, brief structured tasksProblem gate, design system validation, accessibility checks
SonnetImplementation, synthesis, multi-step reasoningArchitect, Designer, iOS Engineer, QA, research compilation
OpusTaste, quality verdicts, final reviewCreative Director, Distinguished Engineer, facilitated reduction
lightbulb

The model assignment matters most at the quality gate. Running everything through Sonnet is fine for drafting; the final ship/no-ship verdict should go to Opus.

How skills differ from prompts

A prompt

"Design the navigation model for this app." Claude responds once. The quality depends entirely on how well the prompt was written. No gates. No structure. No checkpoints.

compare_arrows

A skill

/studio-design triggers: check prior decisions → Historian pass → Strategist evaluation → Architect constraints → Critic reduction → Designer directions → Accessibility review. Pauses for approval at each gate.

Skill evolution

Skills evolve as you learn what sequence produces the best output:

1

Simple slash commands

Single-agent invocations. Fast to write, inconsistent output.

2

Sequenced workflows

Multi-agent sequences with pauses for approval. Consistent structure.

3

Parallel orchestration

Multiple agents run simultaneously. One notification per phase instead of per agent.

4

Multi-model workflows

Haiku for gates, Sonnet for synthesis, Opus for verdicts. Each phase uses the right model.

tips_and_updates

Start with step 1. Build a skill when you repeat the same sequence three times and the sequence matters. Optimize latency only after the sequence is proven.

The System

Memory

Claude has no memory between sessions. Memory files solve this — structured context that loads at session start and accumulates decisions over time.

Two memory tiers

Global memory

Travels with you across all projects. Craft preferences. Process learnings. Things that are true about how you work regardless of what you're working on.

add

Project memory

Scoped to one product or team. Brand principles. System invariants. Decisions made. Things discarded and why. A new session picks up exactly where the last one left off.

What belongs in memory vs. CLAUDE.md

TypeGoes in CLAUDE.mdGoes in Memory
Design principlesYes — behavioral rulesNo
Decisions made this sessionNoYes — persists for next session
Directions discardedNoYes — prevents retreading
Anti-patternsYes — governs behaviorNo
Key file locationsSometimesYes — project-specific state
Named constraintsYes if permanentYes if evolving
warning

Memory files go stale

A memory entry that names a file, function, or decision is a claim about the state of the world when it was written. Before acting on recalled memory, verify it against the current state. Stale memory that contradicts current reality should be updated or removed, not followed.

# [Org Name] — Org Layer Behavioral Contract
# This file is imported by all team CLAUDE.md files.
# Do not edit without AI Tooling review.

## Non-Negotiables

### IP and Data Handling
- Never include real customer data, PII, or transaction details in prompts
- All AI-assisted outputs are company property; do not reference external products in output
- When in doubt about data sensitivity, exclude it from the session

### Accessibility
- All designs must meet WCAG AA contrast minimum
- Touch targets minimum 44x44pt
- Every interactive element requires a screen reader label

### Brand Voice
- Clear over clever
- Direct over decorative
- Customer-first framing in all copy

## AI Behavior Rules
- AI assists; it does not author or decide
- All AI output requires review and approval before use
- Agents and skills are process guides, not guardrails — judgment is always required

## Decision Hierarchy
1. Structural correctness — does this solve the actual problem?
2. Conceptual clarity — is the concept legible without explanation?
3. System coherence — does it fit the design system?
4. Reduction of parts — can anything be removed?
5. Craft precision — is the execution detail correct?
6. Visual refinement — does it look right?

## Anti-Patterns (treat as defects)
- Decorative UI elements with no structural function
- Inconsistent spacing or type usage
- Features added without a necessity test
- AI output accepted without review
